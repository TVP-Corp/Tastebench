# Test Tastebench

| Suite | Command | Where | Needs |
|---|---|---|---|
| Unit and component | `pnpm test` | `src/**/*.test.ts(x)` | nothing |
| Rules and data layer | `pnpm test:emu` | `tests/emu/*.test.ts` | Java 21+ |
| End to end | `pnpm test:e2e` | `tests/e2e/flow.spec.ts` | Java, Chromium |

Run one unit file with `pnpm test src/routes/Rate.test.tsx`.

## Which suite to run

- Domain or UI change: `pnpm test`.
- Change to `firestore.rules` or `src/firebase/rooms.ts`: also `pnpm test:emu`.
- Change to navigation, effects, or a flow the e2e spec covers: also `pnpm test:e2e`.

## Add a unit or component test

- Domain: a `*.test.ts` next to the module, plain inputs and outputs (`src/domain/results.test.ts`). Shared people and entries are in `src/test/fixture.ts`.
- Component: a `*.test.tsx` next to the component. Mock the data layer with `vi.mock('../firebase/rooms', () => ({ ... }))` and `vi.mock('../firebase/app', () => ({ db: {}, auth: {} }))`. Provide `RoomContext.Provider` with a full value (`room`, `participants`, `me`, `isCreator`, `error`, `uid`, `code`). Wrap in `MemoryRouter` when the component navigates.
- Query by role and accessible name. `globals: true` is on, so `describe`, `it`, `vi` need no import in component tests.
- jsdom lacks some browser APIs. Stub them per test (for example `window.scrollTo = vi.fn(() => Promise.resolve())`, which also matches Chrome's return value).

## Add a rules test

- Add a case to `tests/emu/rules.test.ts` inside the matching `describe`. Use `seed(status)` to set the room state, `as(uid)` for the caller, and `assertSucceeds` or `assertFails`.
- Cover the allowed caller and at least one denied caller or state.

## Fix a failing test

1. Run the single file.
2. Read the first failure. Do not change an assertion to match new output without checking that the output is right.
3. A test that passes on broken code is a bug: check that a new test fails without your fix.
