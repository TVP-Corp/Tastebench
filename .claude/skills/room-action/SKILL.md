# Add or change a room action

This recipe threads one action through all three layers and the rules. See `domain-layer`, `data-layer`, `presentation-layer` and `firestore` for the detail of each step.

## Add

1. **Type.** If the action adds a field, add it to `Room` or `Participant` in `src/domain/types.ts`.
2. **Rule test first.** In `tests/emu/rules.test.ts`, add a `describe` with the allowed caller and state (`assertSucceeds`) and the denied ones (`assertFails`): another user, the wrong status, extra keys.
3. **Rule.** Add a branch in `firestore.rules` with `changed().hasOnly([...])` and the status gate. Run `pnpm test:emu` until it passes.
4. **Data function.** Add the function in `src/firebase/rooms.ts`. Map a new field with a default in `subscribeRoom` or `subscribeParticipants`.
5. **UI.** Call it from the screen or component without `await`, with `.catch(console.error)`. Destructive actions open `ConfirmDialog` first. Navigate away before the write when the action removes the current user's access (see `ParticipantList` "Leave room").
6. **Component test.** Add the function to the `vi.mock('../firebase/rooms', ...)` factory of each test file that renders the component, then assert it is called with the right arguments after the confirmation.
7. Run `pnpm test`, `pnpm exec tsc -b` and `pnpm test:emu`. Deploy the rules after the merge.

## Edit

- A changed field name breaks old documents: keep reading the old name with a default, or accept the loss for a one-time event app and say so in the PR.
- Tightening a rule can lock out clients that already have the old app open. Test the old write path with `assertFails` on purpose.
- Every test file that mocks `../firebase/rooms` must list the functions its components import, or the import is `undefined`.
